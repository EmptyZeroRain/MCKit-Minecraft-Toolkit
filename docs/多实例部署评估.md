# 多实例部署评估

> 对应 gj.md 阶段四第 2 项「根据真实访问量评估多实例部署」。
> 结论：**代码层面已具备多实例前提，但当前真实访问量不需要多实例；横向扩容前必须先解决 4 个实例本地状态。**

## 1. 什么时候才需要多实例

先给判定线，避免「为了架构而架构」：

| 信号 | 单实例是否还够 | 处理顺序 |
| --- | --- | --- |
| CPU 长期 > 70%，且主要消耗在 JSON 序列化 / 反编译等可并行请求 | 不够 | 先看单实例纵向扩容（核数 / 内存），再考虑横向 |
| 单实例内存 > 70%，且大头是 mcsrc 缓存或进程内统计 | 不够 | 缓存迁移 / 限流收紧 |
| 可用性要求「单机故障不影响访问」 | 不够 | 至少 2 实例 + 负载均衡 + 共享存储 |
| 峰值 QPS < 200、p95 < 300ms | 够 | 优化慢查询与索引即可 |
| 只读流量高（源码浏览、资料页） | 可以用反向代理缓存顶住 | 加 CDN / 缓存，不急着扩实例 |

**当前状态**：项目定位是社区工具站，单实例 + PostgreSQL 足以支撑；阶段一已把会话从内存迁到可选的 PostgreSQL，
正是为了「真需要横向扩容时不用改业务代码」。因此本次交付的是**评估 + 前置条件清单**，不做部署形态变更。

## 2. 已具备多实例条件的能力

| 能力 | 实现 | 多实例是否安全 |
| --- | --- | --- |
| 会话 | `SESSION_STORE=postgres`（`auth/session_postgres.go`），含过期清理 | 安全（共享表，任一实例可续期 / 撤销） |
| 权限 | 角色权限存库，会话内缓存权限快照 | 安全；改权限后需重新登录才生效（可接受） |
| 后台任务 | `admin_jobs` + `FOR UPDATE SKIP LOCKED`，每实例一个调度协程 | 安全（任务只会被一个实例领走） |
| 运营告警 | `ops_alerts` 去重 + 部分唯一索引 | 基本安全，见 §3.1 |
| 访问统计 | 内存聚合 + `ON CONFLICT ... += EXCLUDED` 落库 | 安全（原子累加，不丢不重） |
| 审计 | 只写 `audit_logs`，保留清理是幂等 DELETE | 安全（重复清理无副作用） |
| 登录失败锁定 | 计数落库 | 安全 |
| MFA 挑战票据 | 落库（一次性消费） | 安全 |
| 业务读写 | 全部走 PostgreSQL，无进程内业务状态 | 安全 |

## 3. 横向扩容前必须解决的实例本地状态

### 3.1 告警评估：每个实例都会跑一遍

`alert.Service.Start(5m)` 在每个进程内启动。多实例时同一规则会被并发评估：

- 正常路径：`upsertActive` 先查后写，部分唯一索引保证最终只有一条未关闭告警；
- 竞态路径：两个实例同时插入，其中一个会拿到唯一键冲突错误，被记进 `summary.errors`（不影响业务，但会污染「本次评估结果」）；
- 自动关闭同样会被并发执行，`WHERE status IN (open, acked)` 使第二次是空操作。

**方案（按成本从低到高）**：
1. 接受重复评估（当前行为）：告警数量少、评估是只读查询，代价可忽略；仅需把唯一键冲突错误降级为 debug 日志。
2. 环境变量 `ALERT_EVALUATOR_ENABLED=false` 关掉除一个实例外的评估协程（运维约定，最简单）。
3. 数据库 advisory lock：评估前 `pg_try_advisory_lock`，拿不到直接跳过（推荐，改动约 20 行）。

### 3.2 限流与并发上限：按实例各自计数

`middleware.RateLimit`（令牌桶）与 `ConcurrencyLimit`（信号量）都是进程内的：

- N 个实例 → 实际全局限流 = N × 配置值；
- mcsrc 的「全局只允许 1 个下载」在 N 实例下变成 N 个并发下载，每个数百 MB。

**方案**：扩容时把 `MC_HEAVY_RPS`、`MCSRC` 相关限流按实例数等比下调；或把重接口（`/mcsrc/jar`、`/prepare`）
用 ingress 规则固定路由到单一实例 / 单实例分组。

### 3.3 mcsrc 缓存：本地磁盘

`MCSRC_CACHE_DIR` 是实例本地目录，多实例会导致：

- 同一版本在 N 个实例各下载一份（带宽与磁盘 N 倍）；
- 缓存列表页看到的是「某个实例」的占用，与实际总量不一致；
- 「重建」任务在 A 实例执行，命中 B 实例的请求仍可能读旧缓存。

**方案**：
1. 共享卷（NFS / 云盘）挂到所有实例 —— 最简单，但要确认 `os.Rename` 语义与并发写；
2. 对象存储 + 本地 LRU —— 改动最大，收益也最大；
3. 明确只让「缓存实例」承载 `/mcsrc/*`，其它实例反向代理过去。

### 3.4 进程内一次性状态

- 登录验证码 / 短票据：已落库，安全；
- `linkhealth` 全量巡检：通过后台任务执行，安全；
- 前端静态资源：由各实例各自提供，无状态。

## 4. 扩容检查清单（上线前逐项确认）

- [ ] `SESSION_STORE=postgres`，且所有实例共享同一数据库（否则会话在实例间失效）。
- [ ] 反向代理开启 **会话粘滞** 不是必需的（会话已共享），但需确保 Cookie `Secure/SameSite` 配置一致。
- [ ] `ALERT_EVALUATOR_ENABLED` 或 advisory lock 已处理，避免 N 倍评估。
- [ ] 限流参数按实例数折算，并在压测中验证全局限流符合预期。
- [ ] mcsrc 缓存目录为共享存储，或 `/mcsrc/*` 固定到单实例。
- [ ] 数据库连接池上限 × 实例数 ≤ PostgreSQL `max_connections` 的 80%。
- [ ] 审计 / 统计保留清理确认可重复执行（已幂等），无需只在一台开启。
- [ ] 灰度：先 1 台新实例接 10% 流量，观察 30 分钟错误率与 p95，再逐步放量。
- [ ] 回滚：保留单实例部署清单，出问题 5 分钟内可退回。

## 5. 结论与建议

1. **现在不扩多实例**：没有证据表明单实例到瓶颈，扩了只会把「本地状态」问题放大。
2. **先做两件低成本准备**（后续单独提任务）：
   - 告警评估加 advisory lock（约 20 行，消除竞态噪音）；
   - 把限流参数写进部署文档，明确「单实例值」与「N 实例折算值」。
3. **触发扩容的信号**：连续 7 天 CPU > 70% 或 p95 > 500ms，且已排除慢查询与缓存命中问题；或出现单机故障导致的可用性事故。
4. 真正扩容时，**优先按 §3.3 处理 mcsrc**：它是唯一「必须共享、且体积大」的本地状态，也是扩容收益最大的部分（源码浏览是重流量）。
