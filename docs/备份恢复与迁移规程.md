# 备份、恢复演练与迁移规程

> 对应 `gj.md` §16.4 / §17 阶段一「建立数据库备份、恢复演练和迁移规程」。

## 1. 备份

- 脚本：`scripts/backup.sh`
- 产物：`backup/mc_tools_YYYYMMDD_HHMMSS.sql.gz`
- 方式：容器内 `pg_dump --no-owner --no-acl`，不依赖宿主机 psql 客户端

**要求**

1. 至少每日一次，建议保留 7 份日备 + 4 份周备；
2. 备份目录必须位于独立磁盘或对象存储，不得与数据库同盘；
3. 备份文件含全量业务数据，须按敏感数据管理（访问控制、传输加密）；
4. **执行任何迁移前必须先备份**（`scripts/migrate.sh` 已内置该步骤）。

## 2. 恢复演练

- 脚本：`scripts/restore-drill.sh`
- 行为：把最新备份恢复到隔离演练库 `mc_tools_drill`，校验迁移版本与关键表，然后删除演练库
- 全程不触碰生产库 `mc_tools`（脚本对演练库名做白名单校验）

```bash
./scripts/backup.sh                 # 先有一份备份
./scripts/restore-drill.sh          # 使用最新备份演练
KEEP_DRILL=1 ./scripts/restore-drill.sh   # 保留演练库供人工检查
```

**校验项**

- `schema_migrations` 最高版本可读；
- `accounts` / `roles` / `resources` / `tools` / `wiki_pages` / `audit_logs` 可查询；
- `accounts` 非空（为空即判定备份不完整）。

**频次**

- 上线前必须完成一次；
- 之后每季度至少一次；
- 重大迁移（含 `DROP` / `ALTER` / 数据回填）前额外执行一次。

## 3. 迁移规程

### 3.1 执行方式

```bash
./scripts/migrate.sh                 # 备份 → 应用全部未执行的正向迁移
./scripts/migrate.sh --to 27         # 备份 → 迁移到指定版本（可前进或回退）
./scripts/migrate.sh --down 1        # 备份 → 回退最近 1 个迁移
SKIP_BACKUP=1 ./scripts/migrate.sh   # 仅限本地开发
```

迁移状态记录在 `schema_migrations`，重复执行安全。

### 3.2 文件约定

- 正向：`NNNN_name.sql`
- 反向：`NNNN_name.down.sql`（**必须有**，由 `TestMigrationsHaveDownFiles` 强制检查）
- 单个迁移文件在**一个事务**内执行，失败整体回滚

### 3.3 上线步骤

1. 备份并完成一次恢复演练；
2. 在预发环境用**生产数据副本**执行迁移；
3. 观察应用启动日志与关键接口；
4. 生产执行迁移（低峰期）；
5. 验证：登录、内容列表、审核、统计各一条主链路；
6. 记录：执行时间、执行人、迁移版本区间、结果。

### 3.4 回退策略

- 优先「前滚修复」（写新的修正迁移），因为部分反向迁移可能丢失数据；
- 确需回退时使用 `--to <上一个版本>`，并在回退前后各做一次备份；
- 涉及数据删除的迁移，其 `.down.sql` 只能恢复结构、不能恢复数据，必须在迁移说明中写明。

### 3.5 自动化保障

- `backend/internal/repository/migrate_integration_test.go`
  - `TestMigrationsHaveDownFiles`：每个正向迁移必须有反向文件；
  - `TestMigrateRollbackRoundTrip`：在隔离 schema 中验证「正向 → 全部回退 → 再正向」。

## 4. 故障处置速查

| 现象 | 处置 |
| --- | --- |
| 迁移中途失败 | 事务已回滚；检查日志修复 SQL 后重跑，不要手工改 `schema_migrations` |
| 迁移后接口大面积 500 | 立即回退到上一版本（先备份），再前滚修复 |
| 需要恢复到某个时间点 | 使用最近备份 + 归档 WAL（如启用）；恢复后重放必要的业务补录 |
| 演练库删除失败 | 手工 `DROP DATABASE mc_tools_drill`（确认无连接后） |
