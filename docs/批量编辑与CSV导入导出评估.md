# 批量内容编辑与 CSV 导入导出评估

> 对应 gj.md 阶段四第 1 项「评估批量内容编辑和 CSV 导入导出」。
> 结论：**导出先做（已落地），导入暂缓（给出前置条件），批量在线编辑只做审核类（已落地）**。

## 1. 现状盘点

| 能力 | 状态 | 位置 |
| --- | --- | --- |
| 用户 CSV 导出 | 已有 | `POST /admin/users/export`、`AdminUsersView.vue` |
| 审计日志 CSV 导出（含安全事件视图） | 已有 | `POST /admin/audit-logs/export`、`AdminAuditLogsView.vue` |
| 资源 CSV 导出（按当前筛选） | **本次新增** | `POST /admin/resources/export`、`AdminResourcesView.vue` |
| 审核批量通过 / 驳回（≤50 条） | 已有 | `POST /admin/{submissions,mods,modpacks,redstone/designs}/batch-review` |
| 内容 CSV 导入 | 无 | — |
| 资源批量在线编辑（多选改字段） | 无 | — |

导出的共同约束（刻意统一）：

- 只读、不分页，单次上限 5000 条（用户导出 10000 条），超出通过 `X-Export-Truncated: true` 明示；
- UTF-8 BOM，Excel 直接打开不乱码；
- 所有字段经 `csvSafe` 处理：以 `= + - @` 开头的值前置单引号，防 CSV 公式注入；
- 导出动作写审计（`audit.export` / `resource.export`），记录条数与筛选条件，能回答「谁在什么时候导出了什么范围」。

## 2. 为什么导出优先

1. **纯读路径**：不触碰业务状态机，最坏情况是导出一份过期数据，可重试，无数据修复成本。
2. **即时价值明确**：运营要用表格做外部核对（版本兼容、链接失效、标签缺失），这正是数据质量页反复暴露的问题。
3. **可审计**：导入无法「撤销」，导出天然可追溯；先用导出跑通「筛选条件 = 导出范围」的一致性，再谈导入。
4. **真实约束在筛选一致性**：本次顺手修复了两个「前端传了、后端忽略」的静默缺陷（资源 `status`、审计 `object_type`/`result`）。这类缺陷会让导出结果与页面不一致，是导入功能最大的隐患来源，必须先清零。

## 3. CSV 导入的评估

### 3.1 适合导入的字段（白名单）

| 资源 | 可导入字段 | 理由 |
| --- | --- | --- |
| 资源基础信息 | `slug`(键)、`name`、`summary`、`source_url`、`license`、`status` | 纯文本、无嵌套、可校验 |
| 资源标签 | `tags`（`|` 分隔） | 关联写入可事务化 |
| 资源版本声明 | `supported_versions` / `loader_types`（`|` 分隔） | 白名单校验后可接受 |
| 发布版本 | 不适合 | 一资源多版本，行内难以表达，需独立子表导入 |
| 配方 / 物品 / 命令数据 | 不适合 CSV | 强结构（JSON），已有导入任务流水线 |

### 3.2 必要性前置条件（缺一不可）

1. **幂等键**：以 `slug` 为唯一键做 upsert；没有键的表格无法安全重复导入。
2. **两阶段提交**：先全量校验并返回逐行错误（行号 + 字段 + 原因），确认后才写入；不做「边校验边写」。
3. **事务边界**：整批或分批（建议 500 行/批）事务；部分成功必须明示，不能静默跳过。
4. **写入审计**：每批一条 `resource.import` 审计，记录文件名、行数、成功/失败数、操作者。
5. **权限分离**：导入需要 `content.resources` + 显式确认动作，不能与「查看列表」同权。
6. **限流与体积上限**：单文件上限（建议 5 MB / 5000 行），避免一次导入把进程内存打满。
7. **变更历史**：导入走与后台编辑相同的更新路径，确保 `content_revisions` 有快照、可回滚。

### 3.3 结论

导入的工程量集中在「校验 + 幂等 + 可回滚」，而不是解析 CSV。当前阶段**不做**：

- 运营的实际痛点是「找不到、看不全」，导出 + 数据质量问题工单已能闭环；
- 项目已有完整的数据导入流水线（物品 / 配方 / 命令），资源导入若另起一套会形成两套校验规则。

**触发条件**：当「资源批量维护」的工单每月超过约 5 次，或单次维护超过 100 条时，再按 3.2 落地。

## 4. 批量在线编辑的评估

### 4.1 已经可用的部分

审核类批量操作（通过 / 驳回）已落地并遵循以下约束，可作为其它批量的模板：

- 单次上限 50 条（`domain.MaxBatchReview`）；
- 每条独立事务，返回逐条结果，部分成功是正常状态；
- 每条成功单独写审计，`after` 带 `batch: true`；
- handler 层先做 UUID 校验，非法 ID 整体 422，不进入业务。

### 4.2 不建议做「多选改任意字段」

理由：

1. **语义不可判定**：把 20 条资源的 `status` 一次改成 `published`，等价于「绕过审核发布」，风险远高于收益。
2. **冲突不可见**：不同资源的兼容性结论依赖发布版本，批量改资源级字段会让「兼容性结论」与「版本声明」脱节。
3. **回滚成本高**：虽然有 `content_revisions`，但一次批量改 50 条会产生 50 个版本，回滚要逐个确认。

### 4.3 建议的替代形态（低风险）

| 需求 | 推荐做法 |
| --- | --- |
| 批量补标签 | 在列表多选后「追加标签」，只增不删，幂等 |
| 批量上下架 | 仅允许 `published ⇄ offline` 两个方向，且需要二次确认 + 影响预览 |
| 批量改来源平台 | 通过导入导出 + 人工核对，不做在线批量 |
| 批量删除 | 不做；删除必须逐条带影响预览 |
