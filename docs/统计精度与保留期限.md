# 统计精度与保留期限

> 对应 gj.md 阶段四第 3 项「根据运营规模调整统计精度与保留期限」。
> 结论：**当前精度（日聚合）与保留期（180 天）与运营规模匹配；本次补上 `admin_jobs` 的保留清理，其余给出调整阈值与迁移步骤。**

## 1. 现在的采集精度

| 数据 | 粒度 | 落库方式 | 进程重启影响 |
| --- | --- | --- | --- |
| API 调用量 / 延迟 | 按天 + 延迟分桶（`api_stats_daily`） | 内存累加，默认 60 秒批量 upsert | 最多丢 60 秒增量 |
| 工具访问 / 使用 / 失败 | 按天 + 工具 slug（`tool_stats_daily`） | 同上，冲突时 `+= EXCLUDED` | 同上 |
| 资源访问 | 按天 + 资源 slug（`resource_stats_daily`） | 同上 | 同上 |
| 搜索词 | 按天 + 归一化词（`search_stats_daily`） | 同上 | 同上 |
| 审计 | 逐条实时写（`audit_logs`） | 不聚合 | 无 |
| 后台任务 | 逐条（`admin_jobs`） | 不聚合 | 无 |
| 运营告警 | 逐条 + 去重（`ops_alerts`） | 实时 upsert | 无 |

**关键取舍**：

- 只记录**路由模板**与**公开 slug**，不记录查询参数、不记录用户身份 —— 精度换隐私，避免统计表变成行为日志。
- 不做秒级 / 分钟级时序：运营的问题是「这周哪类内容没人看」，日粒度足够；秒级会带来 1440 倍行数与写入压力。
- 延迟用**分桶**（而不是记录每次耗时）：可以算 p50/p95 的近似，但不能算精确分位数。这是有意的：精确定时延需要逐请求行，代价远大于收益。

## 2. 现在的保留期限

| 数据 | 配置项 | 默认 | 清理方式 |
| --- | --- | --- | --- |
| 日聚合统计 | `STATS_RETENTION_DAYS` | 180 天 | 采集器每 6 小时检查一次，`stat_date < cutoff` 删除 |
| 审计日志 | `AUDIT_RETENTION_DAYS` | 180 天 | 每小时检查，超期删除 |
| **后台任务** | `JOB_RETENTION_DAYS` | **90 天（本次新增）** | 每 24 小时清理**终态**任务（succeeded / failed / cancelled） |
| 会话 | 会话 TTL | 15 分钟（续期） | 每小时清理过期会话 |
| MFA 登录票据 | 固定 | 5 分钟 | 一次性消费 + 过期清理 |
| 运营告警 | 无 | 永久 | **待定，见 §3.3** |

`admin_jobs` 此前完全没有清理，会随巡检任务无限增长；本次新增 `jobs.Service.PurgeOlderThan` +
`StartRetention`（默认 90 天），只删终态，`pending / running` 无论多旧都保留。

## 3. 调整阈值（按运营规模）

### 3.1 统计保留期

| 运营规模 | 建议保留 | 理由 |
| --- | --- | --- |
| 起步（日活 < 1k） | 180 天 | 覆盖同比对比，表行数仍在百万以内 |
| 成长（日活 1k–10k） | 365 天 | 需要年度趋势；配合按月归档 |
| 成熟（日活 > 10k） | 90 天明细 + 永久月汇总 | 明细只服务于近期运营动作 |

> 经验值：`*_stats_daily` 的行数 ≈ 天数 × 维度基数（工具 / 资源 / 搜索词）。搜索词维度最不可控，
> 若 `search_stats_daily` 超过约 500 万行，应先把保留期降到 90 天，再考虑抽样或只保留 TopN。

### 3.2 审计保留期

审计是**合规与追责**依据，不建议低于 180 天；涉及账号安全（登录 / MFA / 改密）的事件建议 365 天。
若需要分级，正确做法是**按动作前缀分流**（安全事件长期、业务操作短期），而不是整体缩短 ——
`audit.List` 已支持 `ActionPrefixes`，可直接用于分流导出后归档。

### 3.3 运营告警保留期（待定）

`ops_alerts` 目前永久保留。按当前告警触发频率（规则少、去重后同一规则未关闭只有一条），
一年量级在数千行，不是问题。**触发条件**：超过 5 万行，或历史查询明显变慢时，增加
`ALERT_RETENTION_DAYS`（建议 365 天）并按 `status=resolved AND resolved_at < cutoff` 清理；
未关闭告警永不清理。

## 4. 调整步骤（避免一次性大删除）

1. **只改配置**：`STATS_RETENTION_DAYS` / `AUDIT_RETENTION_DAYS` / `JOB_RETENTION_DAYS` 均为环境变量，改完重启生效（无需迁移）。
2. **先预估**：`SELECT count(*) FROM api_stats_daily WHERE stat_date < now() - interval '90 days';`
3. **避免长事务**：清理是单条 `DELETE ... WHERE stat_date < cutoff`，如果命中行数超过约 10 万，
   先手动分批删除（`WHERE ctid IN (SELECT ctid ... LIMIT 10000)`），避免锁表与 WAL 峰值。
4. **观察**：清理后确认 `pg_stat_user_tables` 的 `n_dead_tup` 能被 autovacuum 消化。
